What to expect in a data engineer SQL interview round

2026 · ~9 min read · OfferPilot AI

A 45-minute data engineer SQL screen is not evenly split. Aggregation and filtering take the largest slice, the first questions and the ones you clear to reach anything else. Joins are next, and the failure there is a fan-out that returns a wrong number rather than an error. Window functions arrive last, in one or two questions, and they are the tier that decides whether the write-up says senior. Below: that split in detail, one streak question worked from a stakeholder's Slack message to a query that runs, and the capture sequence for when the schema and the question sit on different scrolls.

What the 45 minutes is actually made of

No public dataset breaks a SQL round into minutes, so treat this as a planning split, not a measurement. It matches the shape of the format: questions get harder in order, and the last one exists to separate candidates who all passed the first three.

The traps that live in the biggest tier

People revise window functions and then lose the round on tier one. The recurring traps, in rough order of how often they cost someone an offer:

  • Counting after a fan-out. A LEFT JOIN from customers to orders repeats each customer once per order. COUNT(*) now counts orders, and SUM(c.credit_limit) adds the same limit five times. Aggregate the child table in a CTE first, or use COUNT(DISTINCT c.customer_id).
  • COUNT(*) against COUNT(col) after a left join. The unmatched row still exists, with NULLs in it. COUNT(*) returns 1 for a customer with no orders, COUNT(o.order_id) returns 0. One of those answers "how many orders", and it is not the first one.
  • NOT IN with a NULL in the subquery. It returns zero rows, silently, because the comparison is unknown rather than false. NOT EXISTS does not behave that way. This is a favourite follow-up precisely because it is so quiet.
  • WHERE against HAVING. Date filters belong in WHERE, before grouping. A filter on an aggregate belongs in HAVING. Putting the date in HAVING works on some engines and scans far more than it needs to.
  • Half-open date ranges. If the column is a timestamp, BETWEEN '2026-04-01' AND '2026-06-30' quietly drops everything after midnight on the last day. Write >= '2026-04-01' AND < '2026-07-01' and say why out loud.

One window function question, from Slack message to running query

Good interviewers phrase the last question the way a stakeholder would, because reading the ask is part of the job. It lands looking like this:

hey, for the retention deck: for each user, what was their longest run of consecutive days they opened the app in Q2? and how many users hit 7 days in a row?

The schema is two tables and a dialect note:

-- PostgreSQL 14
events(user_id BIGINT, event_ts TIMESTAMPTZ, event_name TEXT)
users (user_id BIGINT, signup_date DATE, plan TEXT)

Say the shape of the answer before you type. This is a gaps-and-islands problem: find runs of consecutive values, measure each run, take the longest per user. Three moves get you there.

Collapse events to days

The question is about days, not events, and a user who opens the app forty times on Tuesday still has one day. DISTINCT on the cast date does it, with the quarter as a half-open range.

Subtract a row number from the date

Number each user's days in date order. Inside a run of consecutive days the date and the row number both climb by one, so date - row_number stays constant. A gap moves the date by more than one and the difference jumps to a new value. That constant is the island key, and its actual value is meaningless. Only its constancy matters.

Group by the island, then by the user

Count rows per island to get streak lengths, then take the maximum per user. The second half of the ask falls out of the same CTE with one more line.

with days as (
  select distinct user_id, event_ts::date as d
  from events
  where event_name = 'app_open'
    and event_ts >= date '2026-04-01'
    and event_ts <  date '2026-07-01'
),
islands as (
  select user_id, d,
         d - (row_number() over (partition by user_id order by d))::int as grp
  from days
),
streaks as (
  select user_id, grp, count(*) as streak_len,
         min(d) as started, max(d) as ended
  from islands
  group by user_id, grp
)
select user_id, max(streak_len) as longest_streak
from streaks
group by user_id
order by longest_streak desc;

The second question is one line against the same streaks CTE, and it needs no extra grouping because any island of seven or more qualifies the user:

select count(distinct user_id) from streaks where streak_len >= 7;

Trace three days out loud while you write it. If a user's days are 4, 5 and 9 April, the row numbers are 1, 2, 3 and the differences are 3 Apr, 3 Apr, 6 Apr. Two rows in the first island, one in the second, longest streak two. That thirty-second trace convinces an interviewer you derived the trick rather than memorised it.

The follow-ups this question always gets

  • "Why ROW_NUMBER and not RANK?" Ties. RANK leaves holes after a tie, which breaks the arithmetic. The DISTINCT removes duplicate dates so it does not bite here, but say that you know the choice is not arbitrary.
  • "Does it break across month or year boundaries?" No, and that is the point of subtracting from the date rather than from a day-of-month. To a date type, 30 April and 1 May are one day apart.
  • "Users are in different timezones." event_ts::date resolves in the session timezone. If each user carries a timezone column, cast with (event_ts at time zone u.tz)::date, which pulls the join earlier in the query.
  • "Now do it per week." Truncate to the week, DISTINCT those, and subtract row_number * interval '7 days' instead of a plain integer.
  • "Four hundred million rows. Will this run?" The DISTINCT is the expensive step. A composite index on (user_id, event_ts) where the filter is selective, or a pre-aggregated daily activity table, is the honest answer.

When the schema block and the question are on different scrolls

SQL assessments almost never fit one screen. The DDL or ERD sits at the top, a banner underneath says which engine the queries run against, and the question, its sub-parts and an expected-output table sit below the fold. Crop the question alone and any AI answer invents login_date when the column is event_ts, joins on id when the key is user_id, and picks a dialect at random. The schema shot matters far more here than on an algorithm prompt, where the problem is self-contained.

Box the DDL or the column lists for the tables the question names, types included. A TIMESTAMPTZ against a DATE changes the answer, and so does a nullable foreign key.

Scroll, drag two: the dialect banner and the question

You get roughly three seconds between drags, so decide where you are scrolling before you start. Catch the "queries run against PostgreSQL 14" line in the same box as the question text if the layout allows it.

Scroll, drag three: expected output

The sample result table names the output columns and their order, which is what an automated grader diffs against. This is the drag people skip, and the one that turns a right answer into a passing one.

Enter to send, Esc to abandon

Where this goes wrong, starting with the dialect

A generated query can be logically perfect and still refuse to run on the grader's engine, because window and aggregate syntax diverges hard between databases. Check any answer against the dialect banner before you paste it.

Practise the weighting, not the topic list

Work the tiers in the order the round uses them. Spend most of your reps on aggregation with joins underneath it, because that is where offers are lost quietly, then drill four window patterns until they are automatic: ROW_NUMBER for deduplication, LAG for period-over-period, SUM ...
