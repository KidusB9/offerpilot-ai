Why your Codility performance score is 0% when correctness is 100%

2026 · ~7 min read · OfferPilot AI

Codility grades each task against two groups of hidden tests. The correctness group uses tiny inputs, one element, two elements, forty elements, and only asks whether your answer is right. The performance group uses inputs at the top of the stated constraint, usually around 100,000 elements, and every test in it carries a time limit. A 0% performance score means every test in that second group failed, almost always because your algorithm does work that grows faster than the input does. Your logic is correct. Your complexity is not.

The two numbers, and the grid underneath them

Those percentages are not two opinions about your code. They are two counts. Each task has a fixed grid of hidden tests, each test belongs to one group, and each percentage is the share of its own group that passed. The pair 100% and 0% is not a contradiction, it is the signature of a correct brute force.

Below them the report lists every test by name with its verdict and running time, and prints a line like Detected time complexity: O(N**2). That is measured, not read off your source. Codility times the submission across inputs of growing size, fits the curve, and prints the nearest match in its own notation, where ** means "to the power of". It is an estimate, so it can be approximate, but next to a zero it is confirmation rather than news.

One task, two solutions, ten hidden tests

Take a task in the shape Codility sets. Given an array A of N integers and a target K, return the number of index pairs (i, j) with i < j where A[i] + A[j] == K. The constraints: N is within the range 1 to 100,000, each element within -1,000,000,000 to 1,000,000,000. Those two numbers are the task. The first says what your algorithm may cost, the second what your accumulator has to hold.

Solution A, the obvious one. Two nested loops, for i in range(N) then for j in range(i + 1, N), incrementing a counter whenever the pair sums to K. Four lines, unarguably correct, roughly N * N / 2 pair checks.

Solution B, the one the constraint is asking for. One pass with a hash map of value counts: for each element x, add the number of times K - x has already been seen to the running total, then record x. Every pair counted once, in index order, no second loop. O(N) time, O(N) space.

Both return identical answers on every input. Here is the grid: six correctness tests, four performance tests. Names vary by task, but this is the convention Codility reports use.

That is the whole report in two numbers, and nothing in the correctness group was built to expose the difference.

Where the 60% comes from

Six of the ten tests passed. That is the task score.

Row two is the same algorithm in a faster language. medium_random at N equal to 10,000 is fifty million pair checks, which a compiled language clears and an interpreted one does not, so identical logic lands on 25% or 0%. Row three is not slow at all, and gets its own section below. Row one is still 60%, which is 60 points more than an optimal solution that never compiled.

One caveat. Codility does not publish a universal grid size or weighting, and the hiring company configures which tasks appear, so treat six and four as the shape rather than a constant. Some tasks carry no performance group at all, in which case correctness is the whole score. The direction never varies: failing every performance test caps the task well below full marks, however clean the logic is.

When 0% performance is not about speed

Not every zero is a timeout, and the difference changes the fix. Read the verdict column, not the headline percentage.

  • Runtime error from recursion depth. A recursive walk is fine at N equal to 60 and dies at 100,000. Python's default recursion limit sits around 1,000 frames, so you get RUNTIME ERROR on all four performance tests beside a perfect correctness score. Rewrite it as a loop with an explicit stack.
  • Wrong answer from integer overflow. Row three above. A Java or C# int tops out at 2,147,483,647, so counting pairs in an array where most elements match overflows silently and returns a negative number. Correctness tests use small values and never touch it. Move the accumulator to long.
  • Memory. Anything sized N by N is ten billion cells at the top constraint. It allocates happily on a forty element test and fails on every large one.
Read the upper bound on N before you write a line, and turn it into a budget. Around 100,000 rules out O(N**2) and points at a single pass, one sort, or a hash map. Around 1,000 makes O(N**2) safe. The constraint is not decoration, it is the specification of the algorithm they want.

The three traps behind most performance zeroes

Nearly every quadratic solution that scores zero is one of these three. The first is visible. The other two are not, which is why they survive a read-through.

Nested loops over the same input

Two loop headers walking the array, one inside the other. Solution A in its honest form, catchable by counting indentation levels before you submit. The fix is almost always one of three moves: a hash map for "have I seen this before", a prefix sum array for "what is the total of this range", or one sort followed by two pointers.

A linear search hiding inside a single loop

One visible loop, and inside it if x in seen where seen is a list, or arr.indexOf(x), or list.contains(x), or Array.prototype.includes. Each scans the whole collection, so one loop is quietly N * N. Same trap: list.pop(0), arr.shift() and max(A[i:]) are linear per call. Swap the list for a set or dictionary and membership drops to constant time.

String concatenation in a loop

Strings are immutable in Java, C#, Python and JavaScript, so result += c allocates a fresh string and copies everything built so far. Do that 100,000 times and you have copied roughly five billion characters to build one string, with no nested loop visible anywhere. Collect the pieces in a list and join once, or use a StringBuilder. CPython sometimes optimises the single-reference case, but that is an implementation detail, not a plan.

If you are staring at a report right now: check that the failing verdicts really are timeouts rather than runtime errors or wrong answers, work out which trap you wrote, then recompute your cost against the upper bound on N before touching the keyboard. A 60% you understand is a better position than it looks, because correctness is the half that takes judgement, and you already have it.
